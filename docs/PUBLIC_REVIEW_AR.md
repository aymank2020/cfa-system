## وظيفة المشروع ونطاق المراجعة

واجهة Next.js لأدوات محاسبية وواجهة FastAPI للحسابات والملفات وتنفيذ Python داخل مساحة عمل محلية. أدوات الحساب لها مستهلك واجهة فعلي؛ APIs الملفات والتنفيذ متاحة مباشرة، لكن وصل محرر الواجهة إلى هذه APIs يحتاج متابعة مستقلة.

راجعت بنية الملفات بصورة متكررة، وتعليمات AGENTS المتاحة، وملفات التشغيل والتبعيات والاختبارات والمستهلكين المرتبطين بالتغييرات. جرى العمل في نسخة معزولة؛ لم تتصل هذه المراجعة بخادم إنتاج أو قاعدة بيانات مستخدم أو جلسة دراسة حقيقية. هذه نتائج تنفيذ محلي محدد، وليست ادعاء مراجعة كل سطر أو جاهزية إنتاج شاملة.

## نتائج موثقة

- P1: الحفظ استخدم اسمًا ثابتًا `<name>.tmp`، فيتلف ملفًا يملكه المستخدم أو تتصادم عمليات الحفظ. الاسم المؤقت أصبح فريدًا في نفس المجلد: [backend/app/api/files.py:182](../backend/app/api/files.py#L182).
- P2: subprocess.run كان يعمل داخل async handler ويحجب حلقة الأحداث؛ handler أصبح sync ليستخدم FastAPI threadpool: [backend/app/api/execute.py:68](../backend/app/api/execute.py#L68).
- P2: README زعم عدم وجود الواجهة رغم وجود أدوات المالية؛ صححت الحالة وخطوات التشغيل.

## خطة التغيير المنفذة

1. P1 — حفظ ذري باسم مؤقت فريد وتنظيف الملف المولّد فقط: منفذ.
2. P2 — إخراج التنفيذ المتزامن من حلقة async: منفذ.
3. P2 — اختبار حفظ متزامن وحفظ→تنفيذ→قراءة وتحديث دليل التشغيل: منفذ.

## أولويات المتابعة والفجوات غير المنفذة

1. P1 — عزل تنفيذ الكود داخل container بحدود ذاكرة/CPU وشبكة، ومصادقة ومساحات منفصلة قبل نشره. التنفيذ الحالي يملك صلاحيات عملية الخادم.
2. P1 — تقليص stdout أثناء الالتقاط؛ الحد الحالي يطبق بعد capture_output.
3. P2 — وصل محرر الملفات والتنفيذ في الواجهة ثم اختبار متصفح، وتدقيق مدخلات الحسابات المالية. هذه العناصر غير منفذة.
